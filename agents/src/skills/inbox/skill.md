# Airo Inbox

Installs the Airo Inbox chat widget or a contact form on the site. Both features share the same backend account.

## Architecture

- **Account** — the Airo Inbox tenant for this site. Discovered or auto-created via `inbox__discover_account`. Shared by both the chat widget and contact form.
- **Auth** — tools dispatch calls via `ClientActionService` through the browser to `/api/inbox` (BFF). The BFF validates the user's `auth_idp` cookie and forwards the request. The authenticated builder user is the identity.

### Chat Widget

- **`src/lib/inboxChat.config.json` drives rendering.** The CDN script reads `window._support` to determine what to show. `InboxChatWidget.tsx` merges config into `window._support` from the JSON file.
- **Tools own the config file.** The `setup_widget` and `update_widget_config` tools read, merge, and write `src/lib/inboxChat.config.json` directly. The agent never edits the config file manually.
- **The backend is kept in sync.** The tools update the embeddable on the backend so that widget settings stay consistent when the user edits the widget from other surfaces.
- **Embeddable** — the backend widget config. Holds position, colors, icon. We use the first (default) one per account, or create one if none exist.

### Contact Form

- **The form UI is generated by the agent** — there is no template component. Design the form to match the user's request (fields, layout, styling). The only requirement is that it POSTs to `/api/contact` with the correct shape.
- **`src/server/api/contact/POST.ts`** — Express route that receives form data and forwards it to the backend's `data/conversations` endpoint.
- **`src/lib/contact-form.config.json`** — Runtime config (brandId, categoryId). Written by the `setup_form` tool. Read by the server route at runtime.
- **Runtime submissions require no auth** — the `data/conversations` endpoint is a public endpoint.

## Discover Account (required for both paths)

Before setting up either a chat widget or a contact form, ensure an Airo Inbox account is configured:

```typescript
inbox__discover_account({});
```

Outcomes:
- **`alreadyConfigured: true`** — account is already linked, proceed to the relevant path below.
- **`accountCreated: true`** — a new account was provisioned automatically, proceed to the relevant path below.
- **`noAccounts: true`** — user has no Airo Inbox accounts and no entitlements available. Inform them they need an Airo Inbox subscription.
- **`error`** — display the error to the user.

No user interaction is needed at this step — the tool resolves the account automatically.

After this succeeds, follow **one** of the two paths:
- Chat widget → [Chat Widget Setup](#chat-widget-setup)
- Contact form → [Contact Form Setup](#contact-form-setup)

## Chat Widget Setup

### Step 1: Install Templates

**First-time install:**

```typescript
skill({ action: 'install', skill: 'inbox' });
```

**Re-installing** (e.g., after a template update): pass `overwrite: true`, otherwise the skill loader skips existing files:

```typescript
skill({ action: 'install', skill: 'inbox', overwrite: true });
```

Installs:
- `src/lib/inboxChat.config.json` — widget configuration (managed by tools)
- `src/components/InboxChatWidget.tsx` — side-effect component that reads the config and mounts the CDN script

### Step 2: Wire Up the Widget

```typescript
inbox__setup_widget({ color: '#90ee90' });
```

What it does:

1. Reads `brandId` from memory (errors with `brandNotProvisioned` if missing).
2. Lists embeddables for the brand; reuses the first, or creates one if none exist.
3. Updates the embeddable with the webChat icon + color provided (backend sync).
4. Caches `embeddableId` to memory.
5. **Writes `src/lib/inboxChat.config.json`** with account and color.

Idempotent — re-running is safe. Color is optional (defaults to the account's existing color).

### Step 3: Mount the Widget at the App Root

After `setup_widget` succeeds, edit `src/App.tsx` (or the top-level layout) and render `<InboxChatWidget />` once, outside any route switch:

```tsx
import InboxChatWidget from './components/InboxChatWidget';

function App() {
  return (
    <>
      <Router>
        <Routes>...</Routes>
      </Router>
      <InboxChatWidget />
    </>
  );
}
```

The component is side-effect only (renders `null`). It reads config from `inboxChat.config.json`, sets `window._support`, and injects the CDN script.

**Cookie consent:** The widget only loads after the visitor accepts cookies via the CookieBanner (reads `c2_analytics_consent` from localStorage). If consent hasn't been granted, the chat bubble won't appear.

### Updating Widget Configuration

To change widget settings after initial setup, call the tool:

```typescript
inbox__update_widget_config({ color: '#1e40af', position: 'bottom-right', labelText: 'Ask us a question!' });
```

The tool syncs to the backend and writes the config file — no manual file editing needed. Omit a field to leave it unchanged.

## Contact Form Setup

### Step 1: Ensure Email Channel

```typescript
inbox__ensure_email_channel({});
```

Checks whether the brand has an active email channel (category). Creates one named "Contact Form" if missing. Stores the `categoryId` in memory for use by `setup_form`.

### Step 2: Setup Form

```typescript
inbox__setup_form({});
```

What it does:

1. Reads `brandId` and `categoryId` from memory (errors if missing — run prior steps first).
2. Installs the server route template if missing.
3. Writes `src/lib/contact-form.config.json` with brandId and categoryId.
4. Auto-registers the `/api/contact` route in `src/server/entry.ts`.
5. Returns success with the submission contract.

### Step 3: Generate the Form UI

After `setup_form` succeeds, **generate a form component** tailored to the user's request. The form can have any design, layout, or fields — the only requirements are:

1. It POSTs JSON to `/api/contact` using the submission contract below
2. The body includes `user.email` at minimum
3. It handles loading, success, and error states
4. **EVERY form field that is rendered MUST be read in the submit handler and included in the payload.** No exceptions. If a field appears in the UI, its value must appear in either `user` (email/name) or `conversation.data` (everything else). Never render a field without wiring it into the submission.
5. **Include a honeypot field.** A hidden text input that real users never see. The submit handler must NOT include it in the POST body — the server route drops submissions silently when it is non-empty.

```tsx
{/* Honeypot — positioned off-screen, never included in POST body */}
<input
  type="text"
  name="_gotcha"
  tabIndex={-1}
  autoComplete="off"
  style={{ position: "absolute", left: "-9999px" }}
  aria-hidden="true"
/>
```

Example — a checkbox labeled "Existing customer" must be read and included:

```typescript
const existingCustomer = data.get('existing-customer') === 'on';

body: JSON.stringify({
  conversation: {
    messages_attributes: [{ body: message }],
    data: {
      __gd_contact_form_title: 'Contact Us',
      'Existing customer': existingCustomer ? 'Yes' : 'No',
    },
  },
  user: { email, name },
})
```

### Submission Contract

The form MUST POST JSON to `/api/contact` matching:

```json
{
  "conversation": {
    "messages_attributes": [{ "body": "The visitor's message" }],
    "data": {
      "__gd_contact_form_title": "Contact Us",
      "What can we help with?": "Order Status"
    }
  },
  "user": {
    "email": "visitor@example.com",
    "name": "Visitor Name"
  }
}
```

**Field mapping rules:**

- `messages_attributes[0].body` — ONLY the free-text message/textarea content. Never concatenate other field values into the message body.
- `conversation.data` — ALL additional form fields (dropdowns, radio buttons, checkboxes, hidden fields) go here as key-value pairs. The key MUST be the field's label text (e.g. a dropdown labeled "What can we help with?" with value "Order Status" becomes `"What can we help with?": "Order Status"` in `data`).
- `user.email` / `user.name` — visitor identity fields.
- `__gd_contact_form_title` — always include in `data`, set to the form's heading.

**Do NOT concatenate extra fields into the message body** (e.g. `[${topic}] ${message}` is wrong). Each field must be its own key in `conversation.data` so it appears as structured metadata in the inbox.

The server route handles injecting `category_id` and `__gd_type: "contact"`, resolving the backend host, and forwarding the submission.

## Common Mistakes

- **Manually editing `inboxChat.config.json`.** The tools own this file. Always use `update_widget_config` to change settings — it keeps the backend and config in sync.
- **Modifying existing page content when adding the widget.** Adding the widget is additive — mount `<InboxChatWidget />` at the app root and call the setup/config tools. Do NOT rewrite or restructure the existing page/layout.
- **Re-installing without `overwrite: true`.** The skill loader skips existing files by default.
- **Skipping `discover_account`.** Always call `discover_account` before `setup_widget` or `ensure_email_channel` — it ensures the account is configured.
- **Mounting inside `<Routes>`.** The widget must be at the app root so the script loads on every page.
- **Removing the cookie consent check.** The Airo Inbox script sets third-party cookies and must not load until the visitor opts in.
- **Writing widget visual settings to memory.** Don't — the backend is the source of truth. The only things we store are the pointer IDs.
- **Stuffing extra form fields into the message body.** Never do `[${topic}] ${message}` or similar concatenation. Dropdowns, radios, and other structured fields go in `conversation.data` as separate keys (using the field's label as the key) — only the free-text message belongs in `messages_attributes[0].body`.
- **Omitting the honeypot field or including it in the POST body.** The `_gotcha` input must exist in the HTML but must never be read or sent in the submit handler. If it is populated (by a bot) and included in the body, the server will silently drop the submission.
- **Rendering a form field without wiring it into the submission payload.** Every field in the form UI MUST be read in the submit handler and included in `conversation.data`. If you add a checkbox, dropdown, or any other input, you must also add the code to read its value and send it. A field that only exists in the UI is a bug.
