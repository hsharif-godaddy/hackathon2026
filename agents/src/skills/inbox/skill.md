# Airo Inbox

Installs a chat widget or contact form on the site. Both connect to the Inbox backend, which handles all messaging and email notifications automatically.

## Messaging & Notifications

**The Inbox UI is available in the builder.** Users can view conversations, filter by status (unresolved, waiting on customer, resolved), read message threads, and reply — all from the Inbox tab in the builder. It's correct to say messages "land in your Inbox" or that the user can "view and reply in your Inbox."

**How notifications work:**
- **Chat widget:** When a visitor sends a message, they must enter their name and email before the message is created. The site owner receives an **email notification** and can view/reply in the Inbox UI.
- **Contact form:** When a visitor submits the form, the site owner receives an **email notification** and the submission appears in the Inbox UI. No confirmation email is sent to the submitter — they just see the form's success state.
- The owner can reply from the Inbox UI or **reply directly to the notification email**.
- The customer receives the owner's response via email AND in the chat widget (if the message was sent via the widget).

**Correct framing when explaining to the user:** "You'll get an email notification when someone reaches out, and you can view and reply to messages in your Inbox."

**Email skill prohibition:**
- The backend handles all email sending automatically. **Never** load, invoke, or mention the Email skill for anything related to inbox, contact forms, or chat widget submissions.
- **Never** offer to add confirmation emails or auto-replies to form submitters. If the user asks whether the customer gets a confirmation email, simply say no.

## Architecture

- **Account** — the Airo Inbox tenant for this site. Discovered or auto-created via `inbox__discover_account`. Shared by both the chat widget and contact form.
- **Auth** — handled automatically by the tools. No manual auth setup needed.

### Chat Widget

- **Tools own widget configuration.** The `setup_widget` and `update_widget_config` tools manage all widget settings end-to-end. Never manually edit widget config files.
- **The backend is kept in sync.** The tools update the embeddable on the backend so that widget settings stay consistent when the user edits the widget from other surfaces.
- **Embeddable** — the backend widget config. Holds position, colors, icon. We use the first (default) one per account, or create one if none exist.

### Contact Form

- **The form UI is generated by the agent** — there is no template component. Design the form to match the user's request (fields, layout, styling). The only requirement is that it POSTs to `/api/contact/{formName}` with the correct shape.
- **`src/server/api/contact/[formName]/POST.ts`** — server route installed by `setup_form`. Receives form POSTs and forwards them to the backend.
- **Form config** — written and managed by the `setup_form` tool. Never edit form config files manually.
- **Runtime submissions require no auth** — visitors can submit without being logged in.

## Discover Account (required for both paths)

Before setting up either a chat widget or a contact form, ensure an Airo Inbox account is configured:

```typescript
inbox__discover_account({});
```

Outcomes:
- **`alreadyConfigured: true`** — account is already linked, proceed to the relevant path below.
- **`accountCreated: true`** — a new account was provisioned automatically, proceed to the relevant path below.
- **`noAccounts: true`** — user has no Airo Inbox accounts and no entitlements available. Inform them they need an Airo Inbox subscription.
- **`error`** — display the error to the user.

No user interaction is needed at this step — the tool resolves the account automatically.

After this succeeds, follow **one** of the two paths:
- Chat widget → [Chat Widget Setup](#chat-widget-setup)
- Contact form → [Contact Form Setup](#contact-form-setup)

## Chat Widget Setup

### Step 1: Install Templates

**First-time install:**

```typescript
skill({ action: 'install', skill: 'inbox' });
```

**Re-installing** (e.g., after a template update): pass `overwrite: true`, otherwise the skill loader skips existing files:

```typescript
skill({ action: 'install', skill: 'inbox', overwrite: true });
```

Installs:
- `src/components/InboxChatWidget.tsx` — side-effect component that mounts the CDN script
- A tool-managed widget config file (do not edit manually)

### Step 2: Wire Up the Widget

```typescript
inbox__setup_widget({ color: '#90ee90' });
```

Configures the backend and widget settings. Idempotent — re-running is safe. Color is optional (defaults to the account's existing color).

### Step 3: Mount the Widget at the App Root

After `setup_widget` succeeds, edit `src/App.tsx` (or the top-level layout) and render `<InboxChatWidget />` once, outside any route switch:

```tsx
import InboxChatWidget from './components/InboxChatWidget';

function App() {
  return (
    <>
      <Router>
        <Routes>...</Routes>
      </Router>
      <InboxChatWidget />
    </>
  );
}
```

The component is side-effect only (renders `null`). It reads the tool-managed widget config installed alongside it, sets `window._support`, and injects the CDN script.

**Cookie consent:** The widget only loads after the visitor accepts cookies via the CookieBanner (reads `c2_analytics_consent` from localStorage). If consent hasn't been granted, the chat bubble won't appear.

### Updating Widget Configuration

To change widget settings after initial setup, call the tool:

```typescript
inbox__update_widget_config({ color: '#1e40af', position: 'bottom-right', labelText: 'Ask us a question!' });
```

The tool syncs settings to the backend. Omit a field to leave it unchanged.

## Contact Form Setup

### Step 1: Setup Form

```typescript
inbox__setup_form({ name: "contact-us" });
```

**Parameters:**
- `name` (required) — unique slug for this form. Lowercase alphanumeric with hyphens (e.g. `"contact-us"`, `"support-request"`).

Installs the server route, writes the form config, and registers the route. Automatically ensures an email channel exists for the brand. Requires `discover_account` to have run first. Returns the submission URL on success.

### Custom Notification Email

By default, form notifications go to the user's GoDaddy account email. To route notifications to a different address, use `set_form_email` after setup:

```typescript
inbox__set_form_email({ formName: "support", email: "support@business.com" });
```

To revert to the default, call without `email`:

```typescript
inbox__set_form_email({ formName: "support" });
```

### Multiple Forms

Call `setup_form` multiple times with different names to create multiple contact forms. All forms share the same email channel (brand + category) but can have different notification emails. Each form is accessible at `/api/contact/{name}`.

```typescript
inbox__setup_form({ name: "contact-us" });
inbox__setup_form({ name: "support" });
inbox__set_form_email({ formName: "support", email: "support@business.com" });
```

Calling `setup_form` with the same name again updates that form's config (idempotent).

### Step 2: Generate the Form UI

Load the contact form contract before building the form UI:

```typescript
skill({ action: "loadReference", path: "inbox/templates/sections/contact-form-contract" });
```

Follow its instructions to build the form component. That file contains the submission contract, field mapping rules, and honeypot requirements — all REQUIRED.

## Staff Settings

Read or update the **account-level** notification email. This is the default address where chat messages and contact form submissions are delivered. Requires `discover_account` to have run first.

If the user wants a **different** notification email for a specific form only, use `set_form_email` instead — that sets a per-form override without changing the account default.

### Check current settings

```typescript
inbox__get_staff_settings({});
```

Returns `{ notificationEmail }`. Use this when the user asks what email notifications go to.

### Update settings

```typescript
inbox__update_staff_settings({ notificationEmail: "jane@mail.com" });
```

Changes the account-level notification email. Applies to all chat messages and any contact forms that don't have a per-form override via `set_form_email`.

## Listing Forms

To see what contact forms are currently configured:

```typescript
inbox__list_forms({});
```

Returns `{ forms: [{ name, overrideEmail }] }` or `{ forms: [] }` if none exist.

## Legacy Contact Forms (pre-Inbox)

Before the inbox skill existed, contact forms were created via the **email skill**. These use a completely different architecture:
- A route handler that imports `sendEmail` from `@/server/email`
- A `CONTACT_FORM_RECIPIENT_EMAIL` environment variable/secret for the recipient
- No inbox form config file exists
- No inbox account in memory

**Detection:** If the user asks to update or remove a contact form, and `inbox__list_forms` returns empty, check the app's server routes for files that import `sendEmail` with contact-form-like logic (reading `process.env.CONTACT_FORM_RECIPIENT_EMAIL`, accepting name/email/message from the request body).

**Handling legacy forms:**
- **Remove:** Delete the route handler file and the corresponding form UI component. No inbox tools are needed — these forms have no backend state to clean up.
- **Update (fields, styling, layout):** Edit the form component directly. The submission shape is just `{ name, email, message }` posted to `sendEmail` — there is no `conversation.data` structure or inbox backend involved.
- **Update notification email:** The recipient is stored as the `CONTACT_FORM_RECIPIENT_EMAIL` secret. Use `requestSecrets` to prompt the user for a new value.
- **Migrate to Inbox:** If the user wants inbox features (threaded replies, chat widget integration), set up a new inbox contact form via the normal flow (discover_account → setup_form → generate new form UI), then remove the legacy route and component.

## Removing

### Remove Chat Widget

```typescript
inbox__remove_widget({});
```

Deletes the widget component and config file, clears the cached embeddable ID. After this tool succeeds, you MUST also remove the `<InboxChatWidget />` import and render from `src/App.tsx`.

### Remove Contact Form

```typescript
inbox__remove_form({ formName: "contact-us" });
```

Removes the named form from the config. If it was the last form, also removes the server route and config files entirely.

## Common Mistakes

- **Manually editing widget config files.** Always use `update_widget_config` to change settings — it keeps the backend in sync.
- **Modifying existing page content when adding the widget.** Adding the widget is additive — mount `<InboxChatWidget />` at the app root and call the setup/config tools. Do NOT rewrite or restructure the existing page/layout.
- **Re-installing without `overwrite: true`.** The skill loader skips existing files by default.
- **Skipping `discover_account`.** Always call `discover_account` before `setup_widget` or `setup_form` — it ensures the account is configured.
- **Mounting inside `<Routes>`.** The widget must be at the app root so the script loads on every page.
- **Removing the cookie consent check.** The Airo Inbox script sets third-party cookies and must not load until the visitor opts in.
- **Writing widget visual settings to memory.** Don't — the backend is the source of truth. The only things we store are the pointer IDs.
- **Stuffing extra form fields into the message body.** Never do `[${topic}] ${message}` or similar concatenation. Dropdowns, radios, and other structured fields go in `conversation.data` as separate keys (using the field's label as the key) — only the free-text message belongs in `messages_attributes[0].body`.
- **Omitting the honeypot field or including it in the POST body.** The `_gotcha` input must exist in the HTML but must never be read or sent in the submit handler. If it is populated (by a bot) and included in the body, the server will silently drop the submission.
- **Rendering a form field without wiring it into the submission payload.** Every field in the form UI MUST be read in the submit handler and included in `conversation.data`. If you add a checkbox, dropdown, or any other input, you must also add the code to read its value and send it. A field that only exists in the UI is a bug.
