# RUBICON-343 + 344 — Schema & AEO (generation-only, prompt-driven)

**Date:** 2026-06-05 (revised 2026-06-09 after RUBICON-98 merged to `main`)
**Tickets:** [RUBICON-343](https://godaddy-corp.atlassian.net/browse/RUBICON-343) (Schema & AEO on site create — homepage), [RUBICON-344](https://godaddy-corp.atlassian.net/browse/RUBICON-344) (Schema & AEO on add new page)
**Epic:** RUBICON-97 — [airo-marketing] Visibility: SEO, GEO, AEO
**Base:** `main` (RUBICON-98 merged via #4385)
**Delivery:** one combined PR

## Summary

Make every Airo App Builder homepage (343) and newly added page (344) ship with correct,
business-appropriate JSON-LD structured data, generated by the develop agent at build
time.

This is a **generation-only, prompt-driven** change, modeled exactly on how RUBICON-98
shipped SEO: the work lives almost entirely in the **cached develop primer
(`develop/seo.md`)** plus the **always-loaded `v8.md` worked example**. The agent must be
able to produce everything 343/344 need **from always-loaded context alone** — the
593-line SEO skill is **not** loaded during the initial build, so nothing here may depend
on it.

**Validation, the full-site audit, regression detection, customer-facing surfacing, and
the fix loop are explicitly NOT in this work — they belong to
[RUBICON-345](https://godaddy-corp.atlassian.net/browse/RUBICON-345).** 345's own text
draws the line: *"Create and new-page tickets own first-time correctness"* while 345 is
the post-publish *"safety net."* So 343/344 own **first-time correctness via generation**;
345 owns **everything that checks or surfaces it afterward.**

## Why generation-only (key constraints discovered during brainstorming)

1. **The SEO skill is not in create-time context.** Skill loading is gated until after
   design-preview approval; the develop agent builds the first homepage without it. So the
   primer + worked example must be self-sufficient. (This is why RUBICON-98 walked back the
   earlier `force-load seo skill` approach — commit `3144a7351`.)
2. **The `v8.md` worked example IS always loaded.** `context-manager.ts:131-147` injects
   the template description as the **first system message** ("most important context"),
   on by default, cached before history. So a concrete `@graph` example placed there
   reliably reaches the agent at create time — the most token-efficient lever, and the way
   to add the baseline triad **without growing primer prose**.
3. **No structured create-time business context exists.** Only the freeform
   `initial_prompt`, an optional `fqdn`, and `created_at` are available (verified: `apps`
   table in `agents/src/database/schema.ts`; payload in
   `app/src/app/api/sites/quick-create/route.ts`). A deterministic generator would need its
   own LLM extraction step and still couldn't resolve the canonical domain — so generation
   stays with the building agent, which is the only component that knows the business
   specifics because it is authoring the page content.
4. **Token frugality.** The develop agent's primary job is building a good website. Heavy
   create-time guidance causes regressions elsewhere, so the primer delta is capped at a
   few lines and the worked example stays a tight skeleton.

## What already exists on `main` (RUBICON-98 baseline)

- **`agents/src/prompts/develop/seo.md`** (~29 lines, always loaded, cached): already
  requires on every public page — `<Helmet>` with title (≤60) / description (≤160) /
  absolute canonical / full OG + Twitter, **one** `application/ld+json` block
  (`@context`/`@type`/`name`/`url` min, strong anti-fabrication clause), image-hygiene
  attrs, **exactly one `<h1>`**, heading hierarchy (`h2`→`h3`, no skipping), and sitemap
  auto-sync.
- **`agents/src/prompts/template-descriptions/v8.md`** (`:162`): current JSON-LD worked
  example is a minimal single-type `AboutPage` — does not show the baseline triad.
- **SSR plumbing**: Helmet head (incl. JSON-LD) is server-rendered, present on first byte.
- **`agents/src/evals/seo-generation.spec.ts`**: AC-keyed static prompt-assertion eval over
  the primer (and skill), with negative assertions that keep the cached primer
  skill-agnostic. Build-time, token-free.
- **Post-publish audit** (`SeoValidator.ts` + `seo-audit.ts` + `seo-audit-labels.ts`):
  advisory, already checks JSON-LD **validity** and H1 **presence** per route. Extending
  these checks is **RUBICON-345's** work, not ours.

## Scope

### In scope — RUBICON-343 (homepage at create)
- Homepage emits a universal baseline JSON-LD `@graph`: **`WebSite`**, **`Organization`**,
  **`WebPage`**, plus canonical, title, meta description, `datePublished`/`dateModified`.
- A light type-selection nudge: pick the schema.org `@type` that fits the business; use
  `LocalBusiness` (or closest subtype) when the brief gives a location.
- Fields populated only from create-time context — **no invented/placeholder values**.
- Driven by the `develop/seo.md` primer + the `v8.md` worked example only.

### In scope — RUBICON-344 (new page after create)
- New page emits page-level JSON-LD matching site patterns (Helmet + `JSON.stringify`,
  same `@context`), with **entity references back to the site `Organization`/`WebSite`**.
- Page-purpose `@type` selection (`AboutPage`/`ContactPage`/`FAQPage`/`WebPage`/service
  types), required properties only, no fabricated data.
- AEO structure: exactly one `<h1>`, semantic heading hierarchy (**already in the primer**
  — confirm wording covers new pages), and, when `FAQPage` is used, `mainEntity`
  `Question`/`Answer` entries that mirror the visible FAQ.

### Out of scope
- **All validation / audit work → [RUBICON-345](https://godaddy-corp.atlassian.net/browse/RUBICON-345):**
  new `SeoValidator`/`seo-audit` checks (triad presence, page-appropriate `@type`,
  multi-H1, heading hierarchy, FAQPage sync, required-props, registry reconciliation),
  full-site sweep, customer-facing surfacing, and the fix loop.
- **SEO skill changes** (the category→`@type` table, per-type required-props): not loaded
  at create, so out of scope here; build alongside 345's fix flow if needed.
- Automatic creation of new pages from market/trend signals.
- Any new structured create-time business-context capture (no API/UI/DB-schema changes).
- Deterministic/code-generated JSON-LD; LLM-extraction micro-agent.
- Hard, build-blocking completion gates.

## Components & changes

The **generation change** touches **three** files in the `agents/` service (below). Phase 0
additionally adds eval scaffolding under `evals/gosym-probe/` (evaluator + scenarios +
registry entry) — see Evaluation strategy.

### 1. `agents/src/prompts/develop/seo.md` — minimal primer delta (hard cap: a few lines)
- **343:** reword the single-type JSON-LD bullet (`:20`) so the **homepage** emits the
  baseline `@graph` (`WebSite` + `Organization` + `WebPage`) shown in the template example,
  plus `datePublished`/`dateModified`, plus the one-line type nudge (`LocalBusiness` when
  local). This is a **reword**, not an append — and it must distinguish *homepage* (site
  entities) from *sub-pages*.
- **344:** one line — sub-pages emit a page-purpose `@type`
  (`AboutPage`/`ContactPage`/`FAQPage`/`WebPage`) that **references** the site
  `Organization`, rather than re-declaring it. Single-`<h1>` + hierarchy already present
  (`:24`).
- **Guardrail:** *reference* material → never the primer; *concrete copy target* → worked
  example; primer carries only the non-negotiable rule + pointer. Reviewers reject growth
  beyond the narrow delta.

### 2. `agents/src/prompts/template-descriptions/v8.md` — worked example (the main lever)
- Replace the minimal single-type `AboutPage` example (`:162`) with a tight baseline
  `@graph` **skeleton** for the homepage (WebSite + Organization + WebPage, with dates and
  `LocalBusiness` shown as the conditional business node), plus a short sub-page example
  showing a `WebPage`/page-purpose type that references the site `Organization` by `@id`.
- Keep it a **skeleton** (structure + key fields), not a fully-populated example, to bound
  the always-on token cost (~+150–250 tokens).

### 3. `agents/src/evals/seo-generation.spec.ts` — eval coverage (build-time, token-free)
- Add AC-keyed static assertions pinning the new primer phrases (baseline triad on the
  homepage, page-purpose types + entity reference for sub-pages, `datePublished`/
  `dateModified`, `LocalBusiness`-when-local). Update existing AC mappings as needed given
  343's rewrite. Respect the existing negative-assertion convention that keeps the primer
  skill-agnostic.

## Data flow & edge cases

- **No FQDN at create** → `url`/canonical follows the RUBICON-98 convention (preview URL or
  site-root); we do not invent a domain.
- **No location in the brief** → emit `Organization` only, **not** `LocalBusiness`.
- **Homepage vs sub-pages** → only the homepage declares site-level `Organization`/
  `WebSite`; sub-pages reference them by `@id`. The worked example must make this explicit
  so the agent doesn't re-inject `Organization` on every page.
- **Dates** → agent writes the build-time date; staleness on later edits is acceptable here
  (regression detection is 345's job).

## Evaluation strategy (baseline-first)

The static `seo-generation.spec.ts` only checks that *phrases exist in the primer* — it
never runs the model, so it cannot tell us whether the agent actually generates the triad.
We therefore measure behavior with **`gosym-probe`** (`evals/gosym-probe/`), the runtime
harness that drives a synthetic user through a real build, captures the rendered homepage
HTML, and supports **baseline save + before/after regression comparison**.

**This is a dev-time behavioral eval — distinct from RUBICON-345's production publish-time
`SeoValidator`.** Building it here does not cross the 343/344 ↔ 345 boundary. (The two
share *logic* — parse JSON-LD, inspect `@type` — which may be DRY'd later; not now.)

**No JSON-LD evaluator exists today** (the only SEO scenario checks handoff voice). So we
author it first, using the repo's `new-evaluator` / `new-scenario` skills:

1. **Evaluator** — `evals/gosym-probe/src/evaluators/seo/jsonld-structure.ts`, deterministic
   (regex + `JSON.parse`, no judge-LLM cost). Extracts JSON-LD from captured HTML and
   scores: triad presence (WebSite/Organization/WebPage), valid JSON, required fields
   (`@context`/`@type`/`name`/`url`), exactly one `<h1>`, and fabrication red-flags
   (placeholder phone/address patterns). Unit-tested with fixtures.
2. **Scenarios** — three, to exercise the behavioral unknowns:
   - **local business** (e.g. "bakery in Austin") → expect triad + `LocalBusiness`.
   - **online business** (no location) → expect `Organization`, **not** `LocalBusiness`.
   - **new page** (344) → add an About page → expect `AboutPage` that **references** the
     site `Organization` by `@id`, not a re-declared Organization.
3. **Baseline** — run all three on `main` with multiple trials (`--trials 5`; generation
   is stochastic, judge on pass@k not a single run) and `save-baseline`. Expected baseline:
   JSON-LD present but **triad absent** (today's primer emits one fitting type only).
4. **Change → re-run → compare.** Make the Phase-1 prompt/worked-example edits, re-run, and
   read the harness's automatic pass-rate delta. Green = triad now present across trials.

**Setup note:** gosym-probe needs a local AAB instance (`:4000` + preview `:8443`), a
`.env` with GoCode creds, and control-plane app provisioning — non-trivial first-time
setup. Cost is dev-time only (~10+ model calls per scenario×trial); it does **not** touch
the production token budget.

## Testing

- **Behavioral (primary):** the gosym-probe baseline-vs-after comparison above is the
  signal that the change works.
- **Static (Vitest):** `pnpm --filter @airo/agents test:unit "seo-generation"` — new
  AC-keyed assertions pass; existing assertions still pass after the reword.
- **Manual spot-check:** create a site locally, inspect SSR output for `/` (triad present,
  no fabricated fields); add an About page (page-purpose `@type` referencing site
  `Organization`, single `<h1>`).
- **PR checklist:** `pnpm typecheck`, `pnpm lint`, `pnpm build`; backward compatibility
  (existing single-type pages still render valid JSON-LD); E2E `data-testid`/flows
  unaffected (no UI change).

## Sequencing / delivery

One branch off `main`, one combined PR, built in phases (baseline-first / TDD-for-prompt):

- **Phase 0 — eval + baseline:** author the deterministic JSON-LD evaluator + three
  scenarios (`new-evaluator` / `new-scenario` skills), run on `main`, `save-baseline`.
  Expect red on triad presence.
- **Phase 1 — generation change:** reword `develop/seo.md` + upgrade the `v8.md` worked
  example; update `seo-generation.spec.ts` static assertions.
- **Phase 2 — measure:** re-run the scenarios, compare to baseline, confirm the lift.
  Iterate Phase 1 if trials show gaps.

The eval scaffolding (Phase 0) ships in the same PR as durable regression coverage.
PR description records the AC-interpretation notes and the 343/344 ↔ 345 boundary, and
tags the reporter to confirm.

## Risks

- **Baseline occasionally missing at create** (accepted): prompt-only generation has no
  structural guarantee; 345's audit is the safety net. Mitigated by the always-loaded
  worked example as a concrete copy target.
- **Primer bloat → regressions elsewhere:** the central risk. Mitigated by pushing the
  concrete shape into the worked example and capping primer growth to a reworded bullet +
  one line.
- **Over-injection of site entities on sub-pages:** mitigated by an explicit homepage-vs-
  sub-page distinction in the worked example and the 344 primer line.
