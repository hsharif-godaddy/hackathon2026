Deep Build Workflow System

A passive, DAG-driven step executor that replaces prose-based state inference for the Deep Build orchestrator.

The Problem

The Deep Build orchestrator coordinates sub-agents through a multi-phase pipeline: interview, design, plan, build, verify. Previously, the entire workflow was encoded as a prose decision-loop table in the system prompt. Every turn, the LLM had to re-infer "where am I?" from conversation history and artifact existence, then pick the matching action.

Before

  • State inferred from history each turn
  • Gates skipped (model prefers progress)
  • Steps dropped silently
  • Goals forgotten mid-build
  • Bookkeeping competed with real work

After

  • State persisted, injected every turn
  • Gates enforced by the system
  • Next actions computed from a DAG
  • North Star always in context
  • State advances automatically

Core Idea

Separate two concerns that the prose table conflated:

Which steps Dynamic

Generated per project. A game, admin app, and marketing site get different step plans. This is an LLM judgment call.

Execution discipline Deterministic

Don't skip steps, enforce gates, verify before completing. Applied to whatever steps the plan declares. This is code.

How It Works

1. The agent creates a step plan

After triaging the user's request, the orchestrator calls workflow({ operation: "init" }) with a typed step DAG. Each step declares its type, dependencies, owned files, and verification checks.

2. State advances passively

The agent does its real work — dispatching builders, asking questions, awaiting results. An afterToolExecution hook observes these actions and advances state automatically:

Agent actionAuto-transition
runAgent with inputs.stepIdStep marked in_progress
awaitAgents returns successStep verified + marked done
askQuestion for a gateStep marked blocked
User responds (next turn)Gate auto-resolved to done
awaitAgents returns errorStep marked failed

3. Context injected every turn

The orchestrator always sees its current state via an auto-injected XML context block — no tool call needed to read state:

<workflow_steps>
  <step id="interview" status="done" type="auto">Collect project brief</step>
  <step id="design" status="in_progress" type="auto" deps="brief-review">Create design system</step>
  <step id="showcase" status="pending" type="auto" deps="business-details,design">Build showcase</step>
</workflow_steps>

<next_eligible>showcase</next_eligible>

Key Features

DAG-based eligibility

Next actions are computed from dependency edges. The model can't jump ahead — only steps with all deps satisfied are eligible.

Hard gate enforcement

Gate steps require askQuestion. The system refuses to advance until the user responds. No more silently skipped approvals.

Verification on complete

When a builder finishes, the system runs checks (file existence, tsc) before marking done. Failed steps are marked with reasons.

North Star persistence

Project goals, audience, and voice are stored in the workflow state and injected every turn. The model can't lose sight of the big picture.

Archetype flexibility

The step plan is generated per project. Different archetypes (marketing site, admin app, game) produce different step sequences.

Explicit skips

When pre-supplied inputs satisfy a step, it's marked skipped with a reason — not silently dropped. Every step is accounted for.

Architecture (for engineers)

State storage

Workflow state lives in docs/workflow.json in the app's git repository. It's committed alongside code so that a git revert rolls back both the feature and its completion flag atomically.

Module map

ModulePurpose
workflow/types.tsTypeScript types (WorkflowState, WorkflowStep, etc.)
workflow/workflow-store.tsRead/write JSON, computeNextActions (DAG), validateDisjoint
workflow/workflow-transitions.tsafterToolExecution handler — auto-assign, auto-complete
workflow/workflow-gate-resolver.tsAuto-resolve blocked gates at turn start
workflow/verify-runner.tsRun verification checks (files_exist, tsc, manual)
server/workflow-context.tsBuild XML context message, injected after history
tools/ai-lib-tools/workflow.tsAI-lib tool (init, skip_step, add_steps, etc.)

Agent mode persistence

The setAgentMode tool writes app.agent_mode to KV memory. The agent router checks this between session-cache and conversation-agent lookups, ensuring deep-build apps always resolve correctly on reopen.

Git integration

Deep-build turns use --no-ff merge instead of squash, preserving per-step commits on main. Each step's ownedFiles field drives file-scoped commits. The existing per-message auto-commit serves as a failsafe only.

What the agent explicitly controls

  • workflow({ operation: "init" }) — creating the step plan (requires judgment)
  • workflow({ operation: "skip_step" }) — deliberate skips with a reason
  • workflow({ operation: "add_steps" }) — mid-build re-planning
  • Including inputs: { stepId } when dispatching builders
  • Using askQuestion (not prose) for gate steps

Next Steps

The current passive-observation architecture is prototype scaffolding. The planned evolution flips from post-hoc observation to pre-dispatch validation — a centralized workflow authority with a run/attempt model. See next-steps-authority-model.md for the full roadmap covering:

  • Phase 1: Centralized workflow service with pre-dispatch leasing (canAssignStep → assignStep → launch)
  • Phase 2: Step-aware git (isolated worktrees or baseline+revert)
  • Phase 3: Gate identity + intent classification
  • Phase 4: Context optimization for large plans
