# AAB Multi-User (RBAC) — Product & MVP Alignment

> **Status: historical product spec.** This captures the product/MVP decisions and the cross-team
> alignment table that shaped the feature. For how the system actually works today (FGA relation
> names, enforcement, the collaborator table) see
> [multi-user-architecture.md](./multi-user-architecture.md); for request flows see
> [multi-user-flows.md](./multi-user-flows.md). Where this doc and the architecture doc disagree on
> technical detail, the architecture doc wins. Note that the shipped system went **beyond** this MVP
> spec in two ways: it supports **custom roles** (arbitrary capability combinations, owner-editable),
> and member management is restricted to the **owner only**.

---

## Objective

Enable multiple collaborators on a single Airo-built app, each with their own GoDaddy login
and a clearly defined, limited set of permissions. The app owner invites colleagues (Admin or
Editor role) who can then build, publish, and manage the app without sharing the owner's
credentials.

## Proposed Roles

| Role                                              | Build with AI | Publish / Unpublish | Manage Secrets | Manage Domains | Manage Members | Delete App | Transfer |
| ------------------------------------------------- | ------------- | ------------------- | -------------- | -------------- | -------------- | ---------- | -------- |
| **Owner** (implicit — the C1 who created the app) | yes           | yes                 | yes            | yes            | yes            | yes        | yes      |
| **Admin**                                         | yes           | yes                 | yes            | yes            | yes            | no         | no       |
| **Editor**                                        | yes           | yes                 | no             | no             | no             | no         | no       |
| **Viewer** _(post-MVP)_                           | read-only     | no                  | no             | no             | no             | no         | no       |

## Permissions for AuthZ Team

The following are the exact English strings (user-facing copy) required by the AuthZ / invite-email flow.

| Permission Name          | User-Facing Description                           | Roles         |
| ------------------------ | ------------------------------------------------- | ------------- |
| `aab:app:build`          | Create and edit app content using the AI builder  | Admin, Editor |
| `aab:app:publish`        | Publish and unpublish the live app                | Admin, Editor |
| `aab:app:download`       | Download the app source code                      | Admin, Editor |
| `aab:app:manage_secrets` | Add and update environment variables and secrets  | Admin         |
| `aab:app:manage_domains` | Configure custom domains and DNS                  | Admin         |
| `aab:app:manage_members` | Invite, remove, and change roles for team members | Admin         |
| `aab:app:delete`         | Delete the app permanently                        | Owner only    |
| `aab:app:transfer`       | Transfer app ownership to another account         | Owner only    |
| `aab:app:view_db`        | View database tables and data                     | Admin, Editor |
| `aab:app:edit_db`        | Add, edit, and delete database rows               | Admin, Editor |

## OpenFGA Model

> The original `type app` / `can_*` sketch in this doc was a planning placeholder and is **superseded**
> by the shipped, AuthZ-owned **venture-scoped** model. Tuples are
> `customer:<customerId> → airo_app_* → venture:<ventureId>`, and the BFF resolves `siteId → ventureId`
> before every check. The mapping from the `aab:app:*` permission strings above to the shipped FGA
> relations (`airo_app_build`, `airo_app_publish`, `airo_app_manage_secrets`, …) and the role →
> permission grid live in [multi-user-architecture.md](./multi-user-architecture.md) §4. The shipped
> system also supports **custom roles** — arbitrary capability combinations beyond the Admin/Editor
> tiers below.
